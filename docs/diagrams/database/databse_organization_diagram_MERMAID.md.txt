3. Table Organization

Dimension tables

These store reusable reference-style data.

- dim_site
- dim_subject
- dim_analyte

Core operational tables

These store the main lab pipeline facts.

- sample
- shipment
- assay_result
- workflow_event

Quality / audit table

This stores failed or rejected inputs.

- rejected_record

ML / analytics table

This stores leakage-safe features at sample level.

- feature_sample

4. Relationship Explanation

 dim_site
Stores collection-site information.  
One site can have many subjects and many samples.

 dim_subject
Stores subject-level identifiers and attributes.  
One subject can provide many samples.

 sample
This is the central operational table.  
It connects intake/submission data to subjects and sites.  
A sample can have one shipment record, multiple assay results, and multiple workflow events.

 shipment
Stores API-derived shipment information for a sample.  
Useful for transport delay and temperature features.

 dim_analyte
Stores analyte reference information, such as analyte code, name, canonical unit, and expected reference range.

 assay_result
Stores measured results for each analyte on a sample.  
A sample can have many assay results.  
Versioning and `is_current` allow historical and current-result tracking.

 workflow_event
Stores process/status history for a sample.  
A sample can have many workflow events over time.

 rejected_record
Stores records that fail validation, together with the rule that failed and the reason for rejection.

 feature_sample
Stores ML-ready features created at the sample level, using only information available at prediction time.

 5. Recommended Load Order

The database should be populated in this order:

1. dim_site
2. dim_subject
3. dim_analyte
4. sample
5. shipment
6. assay_result
7. workflow_event
8. rejected_record
9. feature_sample

6. Key Constraints to Enforce

- Every table should have a primary key.
- Business identifiers such as sample_id, subject_id, site_code, and analyte_code should be unique where appropriate.
- Foreign keys should link:
  - sample.subject_key -> dim_subject.subject_key
  - sample.site_key -> dim_site.site_key
  - assay_result.sample_id -> sample.sample_id
  - assay_result.analyte_key -> dim_analyte.analyte_key
  - workflow_event.sample_id -> sample.sample_id
  - shipment.sample_id -> sample.sample_id
- Only one current assay result should exist for a given `(sample_id, analyte_key)` combination.
- History should be preserved using fields such as `is_current`, `active`, or version fields rather than deleting rows.
