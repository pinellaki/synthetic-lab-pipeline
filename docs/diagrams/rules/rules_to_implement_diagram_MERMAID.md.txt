Rule Implementation Notes

Ingestion Rules

The pipeline must read all raw inputs without changing the original files. Every ingested record should keep source traceability fields such as source file, source row, source sheet, source page, or report number.

Standardization Rules

The pipeline should standardize identifiers, dates, booleans, numeric values, units, and status values before validation. This is important because the raw files contain inconsistent casing, mixed date formats, manually typed units, and multiple ways of representing the same concept.

Validation Rules

Rule
   ID    |     Area           | Rule                                                              | Severity | Action 
|--------|--------------------|---  --------------------------------------------------------------|----------|------------------------------------------
| VR001  | sample_submissions | sample_id must be present and unique after standardization        | Critical | Reject duplicate or missing IDs 
| VR002  | sample_submissions | subject_id must match SUBJ-#### and must not contain names/emails | High     | Reject or queue for review 
| VR003  | sample_submissions | collection_datetime cannot be after received_datetime             | High     | Reject or queue for review 
| VR004  | assay_results      | result_value must be numeric and non-negative                     | Critical | Reject invalid result 
| VR005  | assay_results      | unit must map to the canonical unit for the analyte               | High     | Standardize or reject 
| VR006  | assay_results      | only one current result version is allowed per sample/analyte     | Critical | Reject or resolve current-version conflict            
| VR007  | workflow_events    | workflow statuses should follow valid chronological order         | Medium   | Warn and report 
| VR008  | feature_table      | features must respect the prediction-time availability window     | Critical | Block leakage columns 

Rejection and Warning Rules

Critical errors should block the record or load. High-severity errors should be rejected or queued for review. Medium-severity issues should create warnings if the pipeline can safely continue. All rejected records should be written to `data/rejected` with the rejection reason.

Trusted Load Rules

The trusted database load should follow the target schema order:

1. Load dimensions first: dim_site, dim_subject, dim_analyte
2. Load sample records into sample
3. Load result records into assay_result
4. Load workflow history into workflow_event
5. Apply uniqueness, foreign-key, current-version, and soft-delete rules

Feature Table Rules

The feature table must avoid data leakage. The prediction time is immediately after sample intake. Features created after that time must not be used. The target is `needs_repeat_before_review`.

Allowed early features include sample type, collection site, priority, intake temperature, collection-to-received time difference, early shipment information, and manual intake note presence.

Forbidden leakage fields include QC status, review status, approved time, result value, and final workflow status.
